# 万山商业授权与本地版设计

## 目标

让万山的正式版可以复用现有授权管理台，使用卡密激活、设备绑定、远端冻结、Ed25519 签名授权凭证和本地离线宽限；同时保留开发版的本地运行方式，不把服务端私钥、管理员令牌或模型密钥放进安装包。

## 现状约束

- 现有前端已经包含 `/activation` 路由，并调用 `window.electronAPI.license`。
- 现有授权服务保留 `/v1/activate`、`/v1/refresh` 和管理台路由，当前激活请求没有产品字段，卡密默认产品为 `live_replay_xia`。
- 万山后端已经把用户数据放在本机数据目录，并具备本机签名和内容加密工具。
- 公共 GitHub 仓库不能提交授权私钥、管理员令牌、真实 API Key、用户数据库或安装包配置。

## 方案

1. 新增 Electron 授权客户端模块。它从正式包的 `release_config.json` 读取授权域名、公钥、产品代码；开发版使用内存中的永久开发授权。
2. 激活后保存 `activation_id`、刷新令牌和签名授权文档。保存内容通过 Electron `safeStorage` 加密，文件放在用户数据目录，不进入安装目录。
3. 本地验签使用 Ed25519 公钥，校验产品代码、设备指纹、签发时间、到期时间和宽限时间。启动/路由验证时尝试刷新；网络失败只在签名凭证仍处于宽限期内放行，远端明确冻结或停用立即拒绝。
4. 复用现有激活页和 Electron IPC 名称：`getMachineId`、`getInfo`、`activate`、`verify`、`getLastFailReason`、`logout`。这样不改已打包的前端资源。
5. 线上服务端的创建卡密和激活请求增加可选 `product_code`，不传时继续使用原默认产品；管理台增加产品选择，保留现有卡密、设备、冻结和解绑流程。

## 安全边界

- 客户端只内置授权公钥；签名私钥、管理员令牌和数据库留在授权服务器。
- HTTPS 失败不把远端响应当成本地授权；只使用已通过本地签名验证的缓存。
- 客户端不把卡密、刷新令牌、公钥或服务器错误写入日志。
- 现有 `integrity_manifest.json`、发布目录扫描和打包加固继续作为正式包的第二道校验。

## 验证

- 单元测试覆盖授权文档验签、产品/设备/时间拒绝、激活缓存和刷新请求。
- `npm run check`、Node 语法检查和 Python 编译检查必须通过。
- 使用 Playwright 启动开发版和商业配置测试版，验证已有激活页可见、成功激活后能进入小说页、退出后回到激活页。
- 线上修改前先备份部署文件；修改后做 HTTP 健康检查、OpenAPI 检查和旧 API 冒烟测试。
